# Student lab manual — new repository, DEV / TEST / PROD

## 0. Prerequisites

A standard Azure subscription with permission to register an Entra app, create resources, and assign Azure RBAC roles (Owner or User Access Administrator / Role Based Access Control Administrator at the needed scope). GitHub account and permission to create a repository, secrets and environments. Azure Cloud Shell Bash, or Azure CLI installed locally. This project uses GitHub Actions, **not GitLab CI/CD**. GitLab variables do not affect GitHub Actions.

**Never copy the trainer's subscription/client/tenant IDs or federated credential.** Each student uses their own Azure tenant, subscription, and GitHub repository. App Service B1 and monitoring are billable; use DEV first.

## 1. Create a brand-new GitHub repository

1. GitHub > + > New repository. Name it e.g. `lab11-project16-azure-pipeline`; choose private or public.
2. Do **not** initialize with README if you will push the extracted files via Git.
3. Download this ZIP and extract it. Upload **the contents** (including hidden `.github/`) to the repository root, **not** a parent folder. Browser: Code > Add file > Upload files (ensure `.github/workflows/main.yml` is preserved); alternatively:

```bash
cd LAB11-Project16-New-Repo-Student-Lab
git init
git branch -M main
git add -A
git commit -m 'Initial LAB11 Project16 student lab'
git remote add origin https://github.com/<YOUR_GITHUB_OWNER>/<YOUR_REPO>.git
git push -u origin main
```

4. Confirm `https://github.com/<OWNER>/<REPO>/blob/main/.github/workflows/main.yml` opens. The Actions tab should show the workflow.

## 2. Get Azure identifiers and create resource groups

In Azure Portal: **Subscriptions > your subscription > Overview** for Subscription ID; **Microsoft Entra ID > Overview** for Tenant ID. In Cloud Shell:

```bash
az account list -o table
az account set --subscription '<YOUR_SUBSCRIPTION_ID>'
az account show --query '{subscription:id,tenant:tenantId}' -o json
for env in dev test prod; do
  az group create -n "rg-lab11-p16-$env" -l centralindia --tags project=lab11-p16 environment="$env" -o none
done
```

Resource groups can be created before role assignment. For students with limited permissions, an instructor/admin must create the groups and grant the role.

## 3. Register the Entra application (one per student)

1. Azure Portal > **Microsoft Entra ID > App registrations > New registration**.
2. Name `lab11-p16-github-oidc-<student-alias>`; **Accounts in this organizational directory only**; redirect URI blank. Click **Register**.
3. On **Overview**, copy **Application (client) ID** and **Directory (tenant) ID**. The **client ID is not the Object ID**.
4. Go to **Certificates & secrets > Federated credentials > Add credential > GitHub Actions deploying Azure resources**.
5. Enter **Organization/owner** (your GitHub username or organization), **Repository** (your *new* repository), **Entity type = Environment**, **GitHub environment name = dev**, name `github-dev`, audience `api://AzureADTokenExchange`, issuer `https://token.actions.githubusercontent.com`. If the portal asks for **Organization ID** and **Repository ID**, retrieve them from the GitHub API as below. Save.
6. Repeat for `test` (`github-test`) and `prod` (`github-prod`). Three distinct credentials are required because the subject contains the environment name. GitHub OIDC subject formatting may use immutable IDs; **use the subject generated by the current portal UI and compare it with the `subject claim` in GitHub Actions logs if login fails**.

```bash
OWNER='<YOUR_GITHUB_OWNER>'
REPO='<YOUR_REPO>'
curl -fsSL "https://api.github.com/users/$OWNER" | python3 -c 'import json,sys; print("Owner ID:",json.load(sys.stdin)["id"])'
curl -fsSL "https://api.github.com/repos/$OWNER/$REPO" | python3 -c 'import json,sys; print("Repository ID:",json.load(sys.stdin)["id"])'
```

For a **private** repository, the unauthenticated GitHub API may return 404. Use `gh api repos/$OWNER/$REPO --jq .id` after `gh auth login`, or inspect the repository details using authenticated GitHub API access.

**No client secret is created or required.** The GitHub `AZURE_CLIENT_ID` secret contains the non-secret application GUID; it is stored as a secret for consistent GitHub Actions configuration.

## 4. Grant the Entra service principal permission to deploy

1. Azure Portal > Resource groups > `rg-lab11-p16-dev` > **Access control (IAM) > Add role assignment**.
2. Select **Contributor**, choose **User, group, or service principal**, select the **Enterprise application/service principal** corresponding to the newly registered Entra app, and assign.
3. Repeat on `rg-lab11-p16-test` and `rg-lab11-p16-prod`, or have an administrator do this. Prefer resource-group scope rather than subscription-wide Contributor.
4. Wait a few minutes for RBAC propagation. Contributor cannot assign RBAC roles; that is why the instructor/admin may need to perform this step.

CLI alternative (only if you have RBAC assignment rights):

```bash
APP_ID='<APPLICATION_CLIENT_ID>'
SP_OBJECT_ID=$(az ad sp show --id "$APP_ID" --query id -o tsv)
SUB_ID=$(az account show --query id -o tsv)
for env in dev test prod; do
  az role assignment create --assignee-object-id "$SP_OBJECT_ID" --assignee-principal-type ServicePrincipal --role Contributor --scope "/subscriptions/$SUB_ID/resourceGroups/rg-lab11-p16-$env"
done
```

## 5. Configure GitHub environments, secrets, and variables

Open **GitHub repository > Settings > Environments > New environment**. Create **`dev`**, **`test`**, **`prod`** (lowercase exact match). In `prod`, configure **Required reviewers** if your plan/repository supports it; protect production branch and restrict deployment branches. `test` can have optional reviewers. Approval protection availability varies by GitHub plan and repository visibility.

Open **Settings > Secrets and variables > Actions**:

**Secrets tab > New repository secret** (or use environment secrets in each environment):

| Name | Exact value to paste | Where to find it |
| --- | --- | --- |
| `AZURE_CLIENT_ID` | Application (client) ID | Entra > App registrations > your app > Overview |
| `AZURE_TENANT_ID` | Directory (tenant) ID | Entra > Overview or `az account show --query tenantId -o tsv` |
| `AZURE_SUBSCRIPTION_ID` | Subscription ID | Azure > Subscriptions > Overview or `az account show --query id -o tsv` |

**Variables tab > New repository variable**:

| Name | Value | Notes |
| --- | --- | --- |
| `AZURE_LOCATION` | `centralindia` | Can override at environment level if needed |
| `AZURE_RG_PREFIX` | `rg-lab11-p16` | Script creates `<prefix>-dev`, `<prefix>-test`, `<prefix>-prod` |

Repository-level secrets are sufficient when all three environments share the same Azure subscription and app registration. For separate subscriptions/app registrations, define the **same secret names as environment secrets** in each GitHub environment with environment-specific IDs. The workflow's `environment:` field makes these available to that job. Environment-level variables may override repository variables.

**Do not create `AZURE_CLIENT_SECRET`.** This workflow uses OIDC. The environment name `test` must also be used in the Entra federated credential.

## 6. Run the pipeline

GitHub > **Actions > LAB11 Project16 - Azure Bicep and App CI/CD > Run workflow**. Choose `dev` and click Run. A push to `main` that changes the listed paths also deploys **DEV** automatically. Workflow sequence:

1. Checkout and Node.js test.
2. Bicep template and parameter compilation.
3. Environment protection/approval (if configured).
4. OIDC login with `azure/login@v2`.
5. `deploy.sh`: create resource group, validate, What-If, deploy modular Bicep.
6. `deploy-app.sh`: create ZIP in a fresh temporary directory, test archive, deploy to Azure App Service.
7. `verify.sh`: list resources, check App Service, curl `/health`.

Once DEV is healthy, manually run `test`, then `prod` (after reviewers/approvals). **A green workflow means deployment and health check succeeded; it is not a security audit.**

## 7. Verify in Azure Portal and Cloud Shell

Portal > Resource groups > `rg-lab11-p16-dev` > check App Service plan, App Service, Application Insights. App Service > Overview > Default domain > browse; append `/health`. Resource group > Deployments > inspect deployment history. App Service > Deployment Center > Logs (if available) and Application Insights > Live Metrics / Failures.

```bash
az resource list -g rg-lab11-p16-dev -o table
az webapp list -g rg-lab11-p16-dev --query '[].{name:name,host:defaultHostName,state:state}' -o table
APP=$(az webapp list -g rg-lab11-p16-dev --query '[0].name' -o tsv)
HOST=$(az webapp show -g rg-lab11-p16-dev -n "$APP" --query defaultHostName -o tsv)
curl -fsS "https://$HOST/health"; echo
```

Expected `/health` JSON: `{"status":"healthy","environment":"dev","version":"1.0.0"}`. Verify TEST and PROD by substituting environment names.

## 8. Student exercises and test scenarios

- Change the app message in `application/server.js`; commit and push to `main`. Observe automatic DEV redeployment.
- Run workflow manually with `test`; confirm distinct resource group and URL.
- Configure production reviewer and run `prod`; verify approval appears before deployment.
- Temporarily break a Bicep syntax token in a branch and verify the validation job fails (do not merge broken code to main).
- Remove a federated credential in a disposable test environment, observe OIDC failure, and restore it.
- Inspect the `What-If` plan for repeat runs and explain idempotency.

## 9. Troubleshooting

| Symptom | Likely cause / fix |
| --- | --- |
| Actions not listed | `.github/workflows/main.yml` not at repository root or not committed to default branch |
| `AADSTS700213` | Federated credential subject does not match repo and `environment:dev/test/prod`; compare issuer, audience, exact subject and client ID |
| `Permission denied`, exit 126 | `chmod +x scripts/*.sh` or invoke scripts using `bash` |
| `zip error: Zip file structure invalid` | Use `mktemp -d`, then create a *new* ZIP inside it; see corrected `deploy-app.sh` |
| `AuthorizationFailed` | Assign Contributor on target RG to correct service principal, wait for propagation |
| App Service quota/policy failure | Verify SKU, region policy, subscription quota and resource providers |
| `/health` fails | Check App Service logs, startup command, Node runtime, ZIP deployment output; rerun verify after startup |
| `prod` waits | Required reviewers need to approve in GitHub Environments |

## 10. Cleanup and cost control

Delete only lab-specific groups after confirming they contain no other resources:

```bash
bash scripts/cleanup.sh dev
bash scripts/cleanup.sh test
bash scripts/cleanup.sh prod
```

Each cleanup prompts for the exact group name. Azure group deletion is destructive and may take several minutes. Do not delete shared production resources.

## 11. GitLab clarification

This ZIP uses **GitHub Actions**, not GitLab. The equivalent GitLab location is **GitLab > Project > Settings > CI/CD > Variables**, but setting variables there will **not** configure this workflow. To use GitLab, a separate `.gitlab-ci.yml` pipeline and GitLab-to-Entra OIDC trust would be required.
